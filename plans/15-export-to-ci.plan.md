# Export to CI v1 — Development Plan

**Spec:** `specs/15-export-to-ci.md`
**Execution mode:** single implementer

**Two workflow constraints set by the CTO, and they change how phases are gated:**

1. **The implementer writes no tests.** Not one, in any phase — and no other
   agent writes them either: `test-writer` is out of this chain by an existing
   cost decision (`INSIGHTS.md` 2026-08-18, `.claude/skills/impl/SKILL.md:209`).
   What happens to the unproven criteria instead is in `## Tests`.
2. **The fix loop is capped** at two iterations and at most two subagents alive
   at any time (see `## Fix loop`).

The honest cost of (1), stated once here rather than hidden in the phases: a
phase gate can no longer prove behaviour, only that nothing compiled wrong and
nothing already-passing broke. Every `Done when` below is still the real
behavioural claim, but it is **asserted by inspection during the phase and
left unproven and reported** — `plan-verifier` pass 1 names every criterion it
cannot evidence, and `/impl` carries that list into the closing report. A defect
can therefore survive the whole run and ship; the compensating control is that
the list of what was never checked is visible at the end, not that something
catches it.

## Goal / Done when

An agent authored in the studio can be exported from its `CI` tab into a target GitHub repository as a PR containing `.devdigest/agents/<slug>.yaml`, its skill files and `.github/workflows/devdigest-review.yml`, and the new `agent-runner` package running inside that workflow reviews every PR and exits non-zero when `countBlockers(findings, ci_fail_on) > 0` — with no migration, no `@devdigest/shared` change and no `nav.ts` change.

## Prior art and rejected approaches

- **2026-08-07 (`server/INSIGHTS.md:276-286`)** — PR freshness is a side effect of two GET routes, not of any sync job. **Must not be retried:** having the runner (or any CI path) read a server-persisted diff. R10/A10 are the guard.
- **2026-08-07 (`server/INSIGHTS.md:288-294`)** — `loadDiff` has two non-equivalent sources; a shallow clone missing the head returns an *empty* diff rather than throwing, which reads as "clean PR". **Must not be retried:** treating an empty diff as a successful clean review. C9 makes the runner log "no reviewable diff" instead.
- **`server/INSIGHTS.md:265-274`** — the container's dependency on concrete adapter classes is a *known, baselined* arch violation. **Do not "fix" it** and do not regenerate `.dependency-cruiser-known-violations.json` while adding the ci module.
- **`reviewer-core/src/index.ts:9-11` and `mcp/tsconfig.json:22-26`** — a package path-aliasing `@devdigest/shared` and emitting with `tsc` writes those sources under its own `dist/`. Already learned twice. **Do not retry** a `tsc`-emitting runner; bundle with ncc (R13, A13).

## Scope

**In:**
- New server module `server/src/modules/ci/` — routes → service → repository, registered in `server/src/modules/index.ts`.
- `POST /agents/:id/export-ci` serving both `action: 'files'` (preview) and `action: 'open_pr'` (install); `GET /agents/:id/ci-installations`.
- Deterministic generation of `.devdigest/agents/<slug>.yaml`, `.devdigest/skills/<slug>.md` per linked skill, `.github/workflows/devdigest-review.yml`.
- Install: `commitFiles` onto `devdigest/ci` from `base`, `openPullRequest` / `findOpenPr` reuse, one upserted `ci_installations` row per `(agent_id, repo)`.
- New npm package `agent-runner/` — manifest load + Zod validation, own diff computation, skill loading, `reviewPullRequest`, `toReviewPayload` posting, `countBlockers` exit code, fork skip, ncc bundle.
- Client: `CI` tab on the agent editor, four-step export wizard modal, new keys in `client/messages/en/ci.json`.
- The delete-cascade warning on agent delete (R15).

**Out** — things a reasonable reader would assume are included:
- Any ingest route, `ci_runs` write, `agent_runs` with `source='ci'`, or `run_token`. Nothing in this plan writes `ci_runs`.
- Any sidebar entry. `client/src/vendor/ui/nav.ts` is vendored **and** out of scope; the CI tab is reached only from `/agents/<id>?tab=ci`.
- Any database migration or `server/src/db/migrations/**` file.
- Any `@devdigest/shared` edit — including "just widening" `CiFile` or `CiResultArtifact`.
- Any change to `ConfigTab`, `modules/reviews/**`, `client/messages/en/runs.json`, `RunReviewDropdown`.
- CircleCI / Jenkins / CLI generation, `Copy files as a zip`, `post_as: 'pr_comment'`, `.devdigest/memory.jsonl`, an editable preview, a write-permission preflight, a published marketplace action.

## Contract changes

**None.** `CiTarget`, `CiFile`, `AgentManifest`, `CiExportInput`, `CiInstallation` and `CiExport` at `server/src/vendor/shared/contracts/eval-ci.ts:284-357` are consumed exactly as written. `./scripts/check-shared.sh` must report no drift at the end of every phase; it is in the verification matrix for that reason, not because anything is expected to change.

If any phase appears to need a shared edit, **stop** — that is a spec-level change, not an implementation decision.

## PR topology — three pull requests, in this order

The homework for this feature asks that a large technical diff ship separately
so the product PRs stay readable, and that advice **also fixes a defect in an
earlier draft of this plan**: the generator used to embed a runner bundle that a
later phase produced. Putting the runner first removes the cycle.

| PR | Phases | Why it is its own PR |
| --- | --- | --- |
| **A — `agent-runner`** | 1–2 | A whole new npm package plus an ncc bundle. Large, mechanical, and reviewable on its own terms: does it parse a manifest, compute a diff, gate on `countBlockers`, and never call the studio? |
| **C — Export to CI, product side** | 3–7 | The `ci` module, the wizard and the CI tab. Reviewable as a product change once the runner it invokes already exists on `main`. |

PR **B** is the other feature entirely (`plans/14-multi-agent-review.plan.md`)
and shares no files with either of these, so it can be opened and merged at any
point relative to A and C.

**Merge order: A, then C.** B is unordered against both.

The phase numbering below already reflects this: 1–2 are the runner, 3–7 are the
product. `/impl` runs stages in order, so PR A is the natural stopping point
after Phase 2 — open it, merge it, then continue the same plan from Phase 3 in
the same worktree.

## Phases

### Phase 1 — `agent-runner` package: scaffold, manifest, diff

- **What lands:** `cd agent-runner && npm install && npm test` passes; the package loads and validates a manifest and computes a diff from a fixture checkout, with no network.
- **Files:** `agent-runner/package.json`, `tsconfig.json`, `vitest.config.ts`, `.gitignore`, `README.md`, `AGENTS.md` + `CLAUDE.md` symlink; `agent-runner/src/manifest.ts`, `src/diff.ts`, `src/env.ts`. **Fixtures yes, tests no**: `agent-runner/test/fixtures/**` is committed here because Phase 4 exercises it by hand and because it is what any later test would need. `vitest.config.ts` is scaffolded so the package is test-ready if the CTO takes the runner-only exception in `## Tests`.
- **Governing skill:** `repo-conventions` (the packaging rules in `CLAUDE.md` "Conventions"). **Decisions:**
  - **npm, own `package-lock.json`, never pnpm** in this directory. `tsconfig.json` is copied from `mcp/tsconfig.json:22-30` — `noEmit: true` plus the `@devdigest/shared` path alias into `../server/src/vendor/shared/index.ts`, and the comment explaining why the package cannot emit stays.
  - `@devdigest/reviewer-core` is aliased to `../reviewer-core/src` and consumed as source, exactly as the server does.
  - Runtime deps: `zod`, `yaml`, `@octokit/rest`. Dev deps: `typescript`, `vitest`, `@types/node`, `@vercel/ncc`.
  - **The diff parser is owned here** (`src/diff.ts`), ported from `server/src/adapters/git/diff-parser.ts:14` (79 lines) with the same fixture cases. It is not imported from the server, and `reviewer-core` is not modified in this plan.
  - The diff comes from `git diff <base>...<head>` executed with `execFile` and an **argument array** — never a shell string, so a branch named `$(id)` is inert (C11).
  - `AgentManifest.parse` failure → the Zod `path` and `message` are printed and the process exits non-zero (C4). It is never downgraded to a warning.
- **Gate:** `cd agent-runner && npm install && npm run typecheck` (the package has no suite yet — `npm test` is a test-stage gate)
- **Done when** — asserted by running the entry against the fixtures by hand; reported as unverified unless evidenced: a valid fixture manifest parses and an invalid one exits non-zero with a Zod path; the parsed diff for the fixture equals `git diff <base>...<head>` computed in the same checkout (A10, first half); a fixture branch name containing `$(id)` and backticks reaches no shell.
- **Depends on:** nothing. This is now the first phase; `AgentManifest` already exists in `@devdigest/shared`, so the runner has a shape to read before any generator writes one.

### Phase 2 — `agent-runner`: review, post, gate, bundle

- **What lands:** the runner reviews a fixture PR with a stubbed LLM, posts a review, and exits `1` or `0` by the gate. `npm run build` emits a bundle.
- **Files:** `agent-runner/src/index.ts` (CLI entry), `src/review.ts`, `src/github.ts`, `src/log.ts`. **No test files.** These four — `run`, `fork`, `untrusted`, `bundle` — would be the highest-value tests in the repo and nobody writes them; `## Tests` names this as the one place the CTO may want an exception.
- **Governing skill:** `repo-conventions`. **Decisions:**
  - `reviewPullRequest` (`reviewer-core/src/review/run.ts:131`), `toReviewPayload` and `countBlockers` (`reviewer-core/src/index.ts:48-54`) are used as-is. **No gate arithmetic is reimplemented** — `countBlockers(findings, manifest.ci_fail_on) > 0 ? 1 : 0` is the exit code, full stop.
  - The provider is `OpenRouterProvider` from `reviewer-core` (`src/index.ts:58`) for `openrouter`; for `openai`/`anthropic` the runner fails with a clear "provider not supported in CI v1" rather than half-implementing two more clients. *(This narrows R5's provider-key generality at runtime while the generated workflow still names the correct key — call it out at review.)*
  - Skill bodies are read from `.devdigest/skills/<slug>.md` in the checkout and passed as `skills: string[]`. Everything PR-originated — diff, branch, title, body — reaches the model through `wrapUntrusted` (`reviewer-core/src/index.ts:15-19`), the same treatment `server/src/modules/skills/assembler.ts:184` gives non-first-party bodies (R12).
  - Fork detection reads `GITHUB_EVENT_PATH` JSON: `pull_request.head.repo.full_name !== GITHUB_REPOSITORY` → print the reason, post nothing, **exit 0** (C10).
  - Empty diff → log `no reviewable diff`, post nothing, exit 0. It is never reported as a clean review (C9).
  - Missing provider key → fail with the `server/src/modules/_shared/provider-errors.ts:5` message shape and exit non-zero (C8). A review that did not happen never looks clean.
  - Posting failures do not swallow the gate: findings are printed and the exit code still reflects them.
  - The log carries manifest name, model, file and line counts, `groundingSummary`, blocker count and exit code (NFR Observability).
  - `npm run build` = `ncc build src/index.ts -o dist --minify`. Nothing asserts that no `dist/**/vendor/shared/**` path exists in the output (A13) — the implementer checks it once by hand after the first build. The bundle is what the **export commits** as `.devdigest/runner.mjs`, so Phase 1's generator reads it from `agent-runner/dist/` at generation time; the package is never published and needs no `bin` entry.
  - **No HTTP request to the studio, ever.** Nothing will test this, so it is a code-reading obligation: the runner imports no studio client and constructs no URL from config. `/security-review` is the pass most likely to catch a violation (A10).
- **Gate:** `cd agent-runner && npm install && npm run typecheck && npm run build`
- **Done when** — asserted by running the bundled entry against the Phase-3 fixtures with a stubbed provider and reading the exit code; reported as unverified unless evidenced: A9 (exit `1` on a `critical` finding with `ci_fail_on: critical`, `0` when the only finding is `info`), A10 (diff match + zero studio calls), A11 (fork → exit 0, nothing posted, reason names secret unavailability), A12 (runner half — `$(id)`, backticks and `${{ github.token }}` appear only inside the untrusted wrapper), A13 (lockfile is `package-lock.json`, no `pnpm-lock.yaml`, bundle clean).
- **Depends on:** Phase 1.

### Phase 3 — `ci` module: registered, generating, deterministic

- **What lands:** `POST /agents/:id/export-ci` with `action: 'files'` returns a `CiFile[]` for a real agent. The module is registered, so the route is reachable.
- **Files:** `server/src/modules/ci/routes.ts`, `service.ts`, `helpers.ts`, `constants.ts`, `workflow.ts`; `server/src/modules/index.ts` (**one import + one `ci,` entry** at `:34-49`). **No test file.** Nobody writes one — see `## Tests`.
- **Governing skill:** `onion-architecture`. **The decisions, already made — do not re-derive:**
  - Layering is `routes.ts` → `CiService` → `CiRepository`. Phase 1 has **no repository** yet (nothing is written); the service reads agents and skills through `container.agentsRepo.getById()` and `container.agentsRepo.linkedSkills(agentId)` (`server/src/modules/agents/repository.ts:73`, `:223`). It **never** imports `modules/skills/repository.ts` or `modules/conventions/helpers.ts` — `no-cross-module-internals` (`server/.dependency-cruiser.cjs:70`) rejects both.
  - `routes.ts` is the only file naming a status code (`server/src/modules/eval/routes.ts:25` is the template). R14: `post_as === 'pr_comment'` → `ValidationError` naming `github_review` and `none`, before any generation.
  - `helpers.ts` is pure (`helpers-are-pure`, `:35`): `slugify(name)`, `uniqueSlugs(names)`, `agentYaml(manifest)`, `skillFile(skill)`.
  - `workflow.ts` builds the YAML as a plain template string — no YAML serializer dependency, and **no timestamp, uuid, or unsorted map iteration anywhere in any generated byte** (this is what makes A3 hold, since Install regenerates rather than accepting client bytes).
  - Skill slugs come from `slugify(skills.name)` with `-2`/`-3` collision suffixes assigned in `order` ascending. Empty result → `ValidationError` naming the skill (C7). The manifest's `skills` array holds exactly these slugs.
  - The workflow's secret name comes from `SECRET_KEY_BY_PROVIDER[manifest.provider]` (`server/src/modules/settings/constants.ts:9-13`), never a literal.
  - **The invocation contract is owned by the runner, not by this phase.** Phases 1–2 ship `agent-runner`'s CLI first; the generator targets what they built, and `workflow.ts` carries a comment pointing at the runner's entry file so the two cannot drift. Re-ordered deliberately: an earlier draft froze the contract here and implemented it two phases later, which also meant this phase had to embed a bundle that did not exist yet. The run step calls **`node .devdigest/runner.mjs review --agent <slug> --pr ${{ github.event.pull_request.number }} --fail-on <ci_fail_on>`** — the bundled runner committed by the export, exactly as the refreshed `design-mocks/src/20-screen_export.jsx:32` shows — preceded by `actions/checkout` and `actions/setup-node`, and reads `GITHUB_TOKEN`, `GITHUB_EVENT_PATH`, `GITHUB_REPOSITORY`, `GITHUB_BASE_REF`, `GITHUB_HEAD_REF` and the provider key from `env:`. Nothing from the PR is interpolated into a `run:` line (R12/C11). `devdigest/review-action@v1` stays a comment (Decision 9). `permissions:` is `contents: read`, `pull-requests: write`, and every other scope `none`. Every `uses:` is a full 40-char SHA. No `pull_request_target`.
  - Any generated file over 1 MB → `ValidationError` naming the file (NFR Scale).
  - **The runner is committed, not fetched.** The export writes the ncc bundle as `.devdigest/runner.mjs` alongside the manifest, so the workflow runs on the target repo's very first PR with no npm publish, no registry, and no network fetch of our own code. An earlier revision switched this to `npx @devdigest/agent-runner@<version>`; that was reverted after the refreshed design (`20-screen_export.jsx:32`) showed a committed runner, because the npm path leaves every generated workflow red until a release task nobody owns has happened. The cost accepted instead: a large generated file in someone else's PR — which is visible, reviewable, and works.
- **Gate:** `cd server && pnpm typecheck && pnpm arch` · `cd server && pnpm exec vitest run --reporter=dot --exclude '**/*.it.test.ts'` (the whole hermetic suite — **regression only**; this phase adds nothing to it)
- **Done when** — asserted by the implementer running the route twice through `app.inject` in a throwaway script and diffing the two responses, then deleting the script; reported as unverified unless a reviewer evidences it: an agent with two linked skills yields exactly four paths and one with zero yields exactly two with `skills: []` (A4); the workflow string satisfies every A5 assertion (`permissions:` present, every `uses:` matches `@[0-9a-f]{40}` or is commented, no `pull_request_target`, no uncommented `devdigest/review-action`); `OPENROUTER_API_KEY` for an `openrouter` agent and `ANTHROPIC_API_KEY` for an `anthropic` one (A6, server half); `pr_comment` returns 4xx naming the two supported values (A14); a skill named `../etc` is rejected by name (C7); calling the route twice returns byte-identical arrays; `pnpm arch` reports no new violation.
- **Depends on:** Phase 2 — the generator embeds `agent-runner/dist/runner.mjs` and must target the CLI that phase actually shipped.

### Phase 4 — Install: commit, PR, one row

- **What lands:** `action: 'open_pr'` commits to `devdigest/ci`, opens or reuses the PR, writes exactly one `ci_installations` row per `(agent_id, repo)`, and returns `CiExport`. `GET /agents/:id/ci-installations` lists them.
- **Files:** `server/src/modules/ci/repository.ts` (new), `service.ts`, `routes.ts` (extended). **No test files.** Nobody writes them — see `## Tests`.
- **Governing skill:** `onion-architecture`. **Decisions:**

## Tests: nobody writes them, and that is a recorded decision

**Corrected after this plan was first written.** An earlier draft of this
section added a `test-writer` stage. That contradicted a decision already on the
books: `INSIGHTS.md` (2026-08-18) records that the agent set was made
mixed-model on cost grounds — `architecture-reviewer` moved to `sonnet`,
`plan-verifier` pass 1 runs with a `sonnet` override, and **`test-writer` was
dropped from the chain entirely**, because four `opus` agents per feature was the
dominant cost. `.claude/skills/impl/SKILL.md:209` says the same in the skill that
executes this plan: *"It does not write tests. `test-writer` is out of this chain
by choice."* Re-adding that stage would have restored the exact cost the decision
removed.

So the real mechanism, which this plan now relies on instead:

- The implementer writes **only** what a phase explicitly calls for. With the
  CTO's "no tests in this workflow", that is **nothing** — every phase above
  lists no test file.
- `plan-verifier` pass 1 (stage 2 of `/impl`, on `sonnet`) extracts the stated
  items and finds a `path:line` or command output for each. Anything it cannot
  evidence is reported as **`not checkable here`**.
- `/impl` copies that list into the run file under **Unverified acceptance
  criteria** and repeats it in the closing report
  (`.claude/skills/impl/SKILL.md:119-124, 194-197`). The ledger is explicit that
  this gap "is only accepted if it is *visible*" — if a closing report stops
  naming it, the saving has become silent debt.

**What this costs here, stated plainly because it is worse for this feature than
for most.** A1–A15 will land essentially unproven, and the code with the least
coverage is `agent-runner/` — the one package that runs on someone else's
machine, with a `GITHUB_TOKEN` and a provider key in scope, and which cannot be
re-checked locally after the fact. `pnpm typecheck`, `pnpm arch`, `pnpm lint` and
`npm run build` prove that it compiles, layers correctly and bundles clean. They
prove nothing about the fork skip, the exit code, or whether an untrusted PR
title reaches a shell. `/security-review` in the review sequence is the only
thing that looks at those at all, and it reads code rather than running it.

If that trade is not acceptable for the runner specifically, the smallest
deviation is to let the implementer write the four `agent-runner` tests
(`run`, `fork`, `untrusted`, `bundle`) and nothing else — a per-phase exception,
not a stage, and not a fifth agent. That is a decision for the CTO, recorded
here rather than taken.

## Fix loop

Findings arrive from three sources: `plan-verifier`, `architecture-reviewer` and
`/security-review`. There is no test stage to produce a fourth. They are worked
in **one capped loop**.

**Hard caps, both set by the CTO — and they match the chain rather than
competing with it.** `/impl` already owns a fix loop inside its `review` stage
(`.claude/skills/impl/SKILL.md:84-86, 126`), and its stop-and-ask list already
includes *"the fix loop hit round 2 with findings open"* (`:194`). The caps
below restate that boundary for this plan; they do not introduce a second loop.

- **At most two subagents alive at any moment.** The shape that fits the chain:
  `implementation-planner` turning the review report into a remediation plan,
  then one `implementer` applying it — never a third in flight.
- **At most two iterations.** One round is review → remediation plan → build →
  review, which the skill deliberately keeps inside one stage so the count is
  not lost across token boundaries.

**Stop rule — this is the part that matters.** If findings survive iteration
two, **stop**. Do not open a third. Write what is still broken into the run
notes with its `path:line` and hand it back to a human. A loop that keeps going
until it is green is how a plan quietly becomes a rewrite, and the third
iteration is where a fix stops being a fix.

**Rules inside the loop:**

- Every fix traces to a stated finding. No refactors, no drive-by improvements,
  no new scope — `implementation-planner`'s remediation mode exists for turning
  a review report into work, and it takes the smallest fix the reviewer named.
- A finding that needs a spec change is **not** fixed in the loop. It is
  recorded and escalated; changing what gets built is a human's call.
- The baselines stay untouched under all circumstances. Regenerating
  `.dependency-cruiser-known-violations.json` or running `lint --fix` to clear a
  finding is itself a defect, not a fix.
- Re-run only the gates that failed, plus the full suite once at the end of the
  final iteration.

## Traps for this change

- **Registering the module is a separate act from writing it.** `server/src/modules/index.ts:34-49` is a static registry. Omit the entry and `pnpm typecheck` is green while every CI route 404s. Phase 1 is not done until a route responds.
- **`pnpm arch` and `pnpm lint` are baselined** (11 violations, **49** warnings — measured 2026-08-28 on `w8`; `CLAUDE.md`'s 43 is stale). Never regenerate `.dependency-cruiser-known-violations.json`, never `lint --fix`. Green means "nothing new".
- **Generation must be deterministic or A3 is flaky.** No timestamp, no uuid, no unsorted iteration in any generated byte. Sort skills by `order`, then by slug.
- **`commitFiles` is not a force-push** (`server/src/adapters/github/octokit.ts:263-296`). A stale `devdigest/ci` accumulates rather than resets — C1/C2 describe existing behaviour, not new code.
- **`ci_installations.agent_id` is `on delete cascade`** (`server/src/db/schema/ci.ts:7`). The studio's only record of an export vanishes silently while the workflow keeps billing the user's key. That is the whole reason for Phase 7.
- **npm vs pnpm.** `agent-runner/` and `reviewer-core/` are npm; `server/` and `client/` are pnpm. A `pnpm install` in `agent-runner/` produces a `pnpm-lock.yaml` that fails A13.
- **`agent-runner` must not emit with `tsc`.** The `@devdigest/shared` alias pulls those sources into the program; ncc, per `reviewer-core/src/index.ts:9-11`.
- **`server/clones/**` contains a full copy of this repository.** Exclude it from every grep and glob or you will edit `clones/dev-digest/server/src/modules/ci/`.
- **`client/src/vendor/ui/**` is vendored** — `ExportWizardSteps.tsx` and `nav.ts` are read-only here. This plan has no exception.
- **Migrations are generated, never written.** This plan generates none. If a phase seems to need a column, it is a spec change, not a `pnpm db:generate`.
- **Test lanes split by filename.** Only `ci-install.it.test.ts` may touch Postgres; every generation assertion is a string assertion and stays hermetic.

## Risks and unknowns

- **Phase 1 generates a file Phase 4 produces.** The export commits `agent-runner/dist/runner.mjs`, so a generation run before the runner has ever been built has nothing to embed. Either Phase 1 emits a placeholder and Phase 4 makes it real, or Phase 1's generator reads the bundle lazily and fails with a clear message when it is absent. Decide at Phase 1; do not let it surface as an empty file in a user's PR.
- **`commitFiles` against a `devdigest/ci` that has diverged from `base`** — behaviour unverified (`specs/15:340-344`). If it fails, Phase 2 needs a documented recovery ("delete the branch and re-export") rather than new code. ~20 minutes against a scratch repo with a real token.
- **GitHub's error shape when a PR already exists for the head branch** — the discriminating field is unknown (`specs/15:345-347`). Phase 2 mitigates by calling `findOpenPr` *before* `openPullRequest` and again in the catch, so the exact error code never has to be matched.
- **ncc + tsconfig path aliases.** ncc resolves `paths` in practice, but `@devdigest/shared` reaching two directories up into `server/src` is unusual. If it fails, the fallback is an ncc-time alias or a build-time copy of the handful of types the runner needs — **not** a `tsc` emit, and **not** an edit to `server/src/vendor/shared`. Prove this in Phase 3, not Phase 4, by bundling the scaffold early.
- **The runner supports only `openrouter` in Phase 4** while generation names the correct key for all three providers. If the CTO wants `anthropic` agents exportable in v1, Phase 4 grows an adapter; the generated workflow does not change.
- **`client/messages/en/ci.json` may be short more keys than the three identified** (`specs/15:351-354`). If so, they are additions to the same namespace — no plan change, just more keys.
- **Phase 7's file is outside the stated ownership.** If widening is refused, drop Phase 7; A15 goes unmet and should be recorded as such rather than solved elsewhere.

### Review sequence to run *after* implementation

Run in this order; each is cheaper to act on than the next.

1. **`architecture-reviewer` — yes, and it earns its tokens here more than on the sibling feature.** Scope it to `server/src/modules/ci/**`, `server/src/modules/index.ts`, and `client/src/app/agents/[id]/_components/AgentEditor/_components/CiTab/**` + `client/src/lib/hooks/ci.ts`. **What no gate proves:** `pnpm arch` is rule-based and baselined — it catches a route touching the db or a cross-module internal import, but it cannot tell you the service is doing the repository's job, that generation logic leaked into `routes.ts`, or that the wizard holds state it should have derived. On the client there is **no enforcement at all**, so every `frontend-ui-architecture` placement call in Phases 5–7 is unchecked by any command. A new module plus a new package is exactly the shape this reviewer is for. **It will miss:** anything about the runner's runtime behaviour in GitHub, and whether the generated YAML is correct.
2. **`/security-review` — yes here, unlike the sibling feature, and this is the change in the calculus.** Scope it narrowly to `server/src/modules/ci/workflow.ts` (the generated YAML string), `server/src/modules/ci/helpers.ts` (path construction under `.devdigest/skills/`), and `agent-runner/src/{index,github,review}.ts`. **Why it earns tokens here and did not for spec 14:** this feature emits code that runs **outside this repository**, on someone else's runner, with a `GITHUB_TOKEN` and a provider API key in scope. R12/C11 (nothing PR-originated reaches a shell or a workflow expression), R5 (`permissions:` minimal, SHA-pinned, no `pull_request_target`), C7 (no path escaping `.devdigest/skills/`) and R6 (no secret value in a body or a log) are all security requirements that **no gate command can prove** — A5 and A12 assert the happy shape, not the absence of a bypass. **It will miss:** GitHub's own permission semantics and anything about the target repo's branch protection.
3. **`plan-verifier` — yes, but run it on *this plan*, before implementation, not after.** It checks a plan against a spec, so its highest-value slot is now: scope it to the A1–A15 table (`specs/15:253-269`) and ask whether every criterion has a phase that makes it true and a gate that proves it. Running it after implementation degrades it into an acceptance-coverage check, which is still useful but overlaps the gates. **It will miss:** everything the spec did not say — including the four audit gaps above, which is why they are audit rows rather than silent phases. If only one pre-build pass is affordable, this is the one.

**Order and reason:** `plan-verifier` now (a missing phase costs one edit to this file); then build Phases 1–7; then `architecture-reviewer` (a wrong layer costs a file move); then `/security-review` (a leak costs a string change, but you want the code final before you audit it). Running the security pass first would audit code the architecture review is about to move.

Findings from all three feed the single capped fix loop above: **two iterations, two subagents, then stop and escalate.** With nobody writing tests, `plan-verifier` pass 1 is where most of the signal comes from — and much of it will be `not checkable here` rather than `not met`, which is a report, not a failure. Budget for a long unverified-criteria list rather than for red gates.

## Out of scope for the implementer

- **Writing tests. Any test, in any package, in any phase.** Nobody else writes
  them either — see `## Tests`. An implementer who "just adds a quick test" is
  not filling a gap someone else will cover; it is unrequested scope in a run
  that was costed without it.
- Opening a third fix-loop iteration, or running more than two subagents in one.
- Architecture review — a separate agent, scoped as above.
- Security review — a separate agent, scoped as above.
- Deciding Q1–Q4 (`specs/15:331-334`). The plan implements the proposed defaults and keeps them reversible; changing one is a new spec, not a phase edit.
- Widening worktree B's ownership to `AgentCard.tsx` (Phase 7) — a human confirms before that phase runs.
- Publishing a marketplace action, a GitHub App, or automating branch protection.
- Verifying `commitFiles` against a diverged branch and the duplicate-PR error shape — needs a scratch repo and a real token; the spec records both as unestablished.
- Recording the insight at the end: `engineering-insights` writes to `server/INSIGHTS.md` (module registration, generation determinism) and the root `INSIGHTS.md` (the runner packaging boundary), and that step is part of the run, not of any phase's gate.
