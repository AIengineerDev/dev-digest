# Onboarding Tour — Development Plan

**Spec:** `specs/11-onboarding-tour.md` (draft)
**Execution mode:** parallel tracks — recommended, see *Execution mode* below; a single-implementer fallback is spelled out at the end.

## Goal / Done when

A developer who opens `/repos/:repoId/tour` on an imported, indexed repository sees five sections — architecture, critical paths, how to run, guided reading, first tasks — where every path resolves against the index **at render time**, every command came from a whitelist derived from that repo's own config files, and every difficulty label carries the caller count and rank percentile it was computed from; generated by exactly two concurrent structured model calls, cached on the repo-state key so a second view costs nothing, and degraded-with-an-explanation rather than `5xx` on every failure — where today `getCriticalPaths`, `getTopFilesByRank`, the `Onboarding*` contracts, the `onboarding` table, the `onboarding` feature-model entry, `onboarding.system.md` and `client/messages/en/onboarding.json` all exist and have **no call site whatsoever**.

## Scope

**In:**
- `GET /repos/:id/tour` (`200` + `TourRecord | null`, with R11 read-time re-resolution) and `POST /repos/:id/tour` (`{force?}`, rate-limited 5/min).
- A new `server/src/modules/tour/` module: routes, service, repository, a pure derivation layer, a pure assembly layer, its **own** pure grounding, a pure step whitelist, a pure difficulty rubric, constants.
- Three additive read methods on the `RepoIntel` facade, and the promotion of `discoverDocuments` to `modules/_shared/`.

## Traps for this change

- **`server/clones/**` holds a full copy of this repository**, including copies of every file this plan edits. Exclude it from every grep and glob or you will read and change the wrong `service.ts`.
- **The `repoIntel` facade does not expose what R2/R3/R10/R11 need** (audit row 1). `getEdges`, `getRankedPaths` and `getFileFacts` are on `repo-intel`'s **repository**, and `no-cross-module-internals` counts `import type` (`tsPreCompilationDeps: true`, `.dependency-cruiser.cjs:113`). Phase T2 is the only legal door.
- **`modules/blast` is the wrong door for R9.** It is PR-scoped (`blast/service.ts:27`), that is deliberate (`specs/08-blast-radius.md:56-59`), and importing it trips the same rule. The arbitrary-file entry point is `container.repoIntel.getBlastRadius(repoId, files)`.
- **`modules/brief/grounding.ts` cannot be imported** (`:118`). This module gets its own, and it is a different shape anyway.
- **`getCriticalPaths` is not a UI-to-DB trace.** It greedily follows the highest-ranked import target from the top 5 ranked files, two hops (`service.ts:670-713`), over a JS/TS-only index (`repo-intel/constants.ts:16`) that knows nothing about SQL, HTTP clients or layers. Honest as "the chains most of the code depends on"; a lie as "how a request reaches the database". The **section title given to the model** is where this goes wrong, which is why T4 fixes the template first.
- **The seeded demo repo cannot exercise `repo-intel` at all** (`server/INSIGHTS.md:129-141`). Four of five sections are `repo-intel`-backed. A green `pnpm test` plus a green e2e flow proves the *degraded* path only. J1 step 5 is not optional.
- **`SimpleGitClient.readFile` throws ENOENT** (`adapters/git/simple-git.ts:128-130`) and has **no traversal guard**, while `MockGitClient.readFile` returns `''` and never throws (`server/INSIGHTS.md:318-329`). Every config read is individually caught, and any C6 / `clone_unavailable` test uses a throwing subclass or it asserts the wrong branch and still passes.
- **`JSON.stringify` of a Zod schema is not a JSON schema.** R14's addend is `toJsonSchema(schema, name).schema` from `@devdigest/reviewer-core` — the object the adapter actually sends (`anthropic.ts:153`, `openai.ts:119`).
- **The pre-flight counter is a floor, not the billed number.** 612 vs 2 006 measured on the brief (`server/INSIGHTS.md:286-302`), on a *smaller* schema. Counting the serialized schema closes most of it; A18 makes the residual visible.
- **`renderTemplate` leaves unknown `{{placeholders}}` intact** (`platform/prompts.ts:33-37`). `onboarding.system.md:42` carries `{{language}}` alongside `{{sections}}`; omit it and the literal string goes to the model.
- **`onboarding.system.md` is half-right and half-wrong.** It names `routes_and_apis` (`:8,23-26`), which this spec drops, and invites the model to author the architecture diagram (`:27`), which R2 forbids. Treating it as finished reintroduces a section nobody asked for and a diagram nobody grounded.
- **The `onboarding` table cannot hold the cache key** — one row per repo, no key columns (`schema/context.ts:120-126`). Persisting into it silently discards R12 and the tour never goes stale. New table.
- **Migrations are generated, never written.** Edit `schema/context.ts`, run `pnpm db:generate`. Add-only on a new table is one clean pass; the two-generate rule applies only when one table both adds and drops columns.
- **`text('col', {enum})` in Drizzle is TypeScript-only** (`server/INSIGHTS.md:331-338`) — no PG constraint, and nothing enforces that the column's list and the Zod enum agree. R19's five-value narrowing is an application claim; **A25 is what makes it real.**
- **`client/messages/en/onboarding.json` describes a different feature** (`:10`) and carries a bare `{count}` (`:4`). Shipping against those strings ships a CTA that promises the wrong five sections.
- **`activeKeyFor` currently maps `/onboarding` → `"onboarding-tour"`** (`app-shell/helpers.ts:29`). Once the nav entry exists, the add-repository wizard highlights the tour. Fix both lines in B1.
- **`client/src/vendor/ui/nav.ts` is vendored.** The edit is deliberate and precedented (`client/INSIGHTS.md:162-175`), isolated to B1 so it can be reverted alone. `nav.ts:33-35` forbids the entry before the screen exists — it lands **with** B1's page, not before.
- **`/onboarding` is the add-repository wizard** (`client/src/app/onboarding/page.tsx`, mock 15, `e2e/specs/06-onboarding.flow.json`). Wiring the tour there replaces a shipped screen. The tour is `/repos/[repoId]/tour`.
- **Not a monorepo.** `server/` and `client/` are **pnpm**; `e2e/`, `reviewer-core/` and `mcp/` are **npm**. J1 step 4 is the npm one.
- **Two gates are baselined:** `server pnpm arch` ignores **10** known violations (not 11 — `CLAUDE.md` is stale), and `client pnpm lint` exits 0 with 43 pre-existing warnings. Green means "nothing new". Never regenerate the arch baseline; never `lint --fix` the warnings as part of this feature.
- **Never `docker compose down -v`** to reset the test database — `-v` destroys `devdigest_pgdata` and every imported repo and review with it.
- **No transactions exist anywhere in the server.** Generation is a single upsert, so nothing here needs a boundary — but do not add a second write to that path without moving the boundary into the service.
- **CI is path-filtered** — five workflows, each scoped to its own paths. A change outside a filter is checked by nothing. The gates in this plan are the gates that matter.
- **A feature can ship inert.** `modules/index.ts`, `hooks/index.ts`, the message keys and the `src/prompts` → `dist/prompts` copy are the four lines that merge cleanly and leave nothing working (`INSIGHTS.md:381+`). J1 step 7 exists only for this.

## Risks and unknowns

- **The five section payloads are frozen at T1 and both tracks build against them.** If Track A discovers that `tree[].role_mix` needs structure, or that `paths[].endpoints` must carry a method as well as a route, both tracks stop, the contract changes server-side once, `--fix` re-mirrors, and both resume. Mitigation: T1 lands the field list at full fidelity from the spec (`:260-273`) rather than incrementally.
- **The 7 000 / 4 000 ceilings are reasoned, not measured** (`:425-430`). The only ratio in this repository is the brief's 612-vs-2 006, on a much smaller schema and a different provider. If the real ratio for this schema is worse, R14's refusal (`input_over_budget`) becomes the common path rather than the exception on any repo of size. **Nothing in the plan changes** — but both ceilings live in `modules/tour/constants.ts`, so retuning is one edit, and J1 step 6 is the measurement that decides.
- **`deepseek/deepseek-v4-flash` has never been called by any code path** (`:419-424`). With `maxRetries: 0`, a malformed structured response is a degradation, not a retry — so if that model handles this schema size badly, the feature will look broken for a configuration reason. Detectable immediately at J1 step 5. If it is bad: the fix is a `FEATURE_MODELS` default change plus the client mirror, one line each, and it is a **spec/CTO decision**, not the implementer's.
- **`getCriticalPaths` on a real repository is unmeasured** (`:431-436`). It may return five near-identical chains through the same hub file, in which case R3's section needs a deduplication rule and the section as specified is the wrong shape. Its only dedup today is on the whole joined chain key (`service.ts:704-706`), which does not catch "five chains sharing a tail". **~30 minutes to check at J1 step 5**; if it reads badly, that is a spec revision, not a plan repair.
- **The distribution of first-task candidates is unmeasured** (`:437-441`). A repo with 400 TODOs and one with none are both handled (the 12 cap and C7), but which is typical decides whether the section is useful or noise.
- **`container.codeIndex.grep`'s pure-Node fallback may be too slow** on a 12 450-file repo for the 10 s derivation budget (`:442-445`); `@vscode/ripgrep` is an optional runtime dependency (`ripgrep.ts:28-40`). **~20 minutes to check in A2.** If it is too slow, the `todo_marker` generator gets its own timeout and yields zero on expiry — which is already its documented failure mode (`:248`), so the fix is a constant, not a redesign.
- **Unknown, ~10 minutes to check in T1:** whether narrowing `OnboardingSection.kind` from `z.string()` to an enum breaks any client fixture. It should not — the shape has zero consumers today — but `INSIGHTS.md:356-366` records exactly this class of change breaking test files in modules the task never touched. `pnpm typecheck` in both trees answers it by name.
- **Unknown, ~10 minutes to check in T4:** whether the production build already copies `src/prompts` → `dist/prompts`. `platform/prompts.ts:12-14` says it must, and `onboarding.system.md` becomes the first template loaded by a **route** rather than an offline path. A missing copy step is a production-only failure no test catches.
- **`file_facts.endpoints` population is assumed, not verified.** The column exists with a `[]` default (`schema/repo-intel.ts:80`) and `modules/blast` reads it, but I did not confirm the indexer populates it for a real repo. If it is empty in practice, R3's endpoint annotation and R8's `undocumented_endpoint` generator both silently yield nothing — a quiet degradation, not a failure. Checked at J1 step 5.
- **R11 adds a `getIndexedFiles` call to every `GET`.** For a 12 450-file repo that is one indexed query plus a set pass, which should sit inside the 400 ms warm bound, but it is not measured. If it does not, the fallback is caching the path set per `(repoId, indexed_sha)` in process — no contract change, no migration.

Cost later: an implementer concludes the file was replaced and rewrites it from scratch, losing the SECURITY paragraph that R16 depends on.

One clause naming `toJsonSchema` removes the single most likely silent misimplementation in R14.

## What differs if a single implementer is chosen

- **The trunk is unchanged** — T1 → T2 → T3 → T4, same order, same reasons. T2 in particular is not a parallelisation artefact; without it Track A cannot compile.
- **Tracks become one sequence:** T1 → T2 → T3 → T4 → A1 → A2 → A3 → A4 → A5 → B1 → B2 → B3 → J1 → J2. Server before client throughout, because the phase that makes the feature *exist* (A4, the two grounded calls) must precede the phase that makes it visible.
