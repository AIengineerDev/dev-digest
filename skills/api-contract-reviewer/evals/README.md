# Eval suite — DELIBERATELY BREAKING, DO NOT SHIP

Four synthetic pull requests against a pretend published package,
`packages/public-api`. Three of them break the contract in three different ways
each; the fourth breaks nothing and exists to catch a reviewer that reports
everything.

The fixture files themselves say **nothing** about what is planted — no
`// BUG:` markers, no leading comments, no giveaway naming. Everything a
reviewer would need to cheat lives in this README and in `expected.json`, and
neither ever reaches the prompt: the engine sees only the generated diff.

**Nothing here is reachable from the product.** Like `fixtures/security-demo`,
this directory sits outside every package: no `tsconfig` `include`, no test
glob, no `dependency-cruiser` scan, no build. The `.ts` files import modules
that do not exist (`../store.js`, `fastify`) — they are diff material, not code.
It lives inside the skill, not in `fixtures/`, so the skill and the evidence it
works ship as one folder.

## Layout

| Path | What |
| --- | --- |
| `baseline/` | v2.3.4 of the contract package — the "before" side of every diff |
| `cases/<id>/` | the "after" side: the files that PR changes, overlaid on `baseline/` |
| `diffs/<id>.diff` | generated by `./make-diffs.sh`; **this** is what the reviewer sees |
| `expected.json` | the answer key, plus which prompt and which skills the harness attaches |

Never hand-edit `diffs/`. Change `baseline/` or a case, then re-run
`./make-diffs.sh` — the hunk headers have to be real or the engine's
citation-grounding gate drops every finding regardless of whether it was right.

## What is planted, and what should be found

Nine contract changes across three cases. The table mirrors `expected.json`;
change one and change the other.

### `01-tidy-the-pr-payload` — reads like a naming cleanup

| id | File | Planted change | Severity we expect |
| --- | --- | --- | --- |
| `01-a` | `contracts/pulls.ts` | `head_sha` renamed to `headSha`, no compatibility alias — every client reads `undefined`, silently | CRITICAL |
| `01-b` | `contracts/pulls.ts` | `last_reviewed_sha` removed outright, never deprecated | CRITICAL |
| `01-c` | `package.json` | two breaking changes shipped as a **patch** bump, 2.3.4 → 2.3.5 | CRITICAL |

### `02-in-flight-runs` — reads like a nullability fix

| id | File | Planted change | Severity we expect |
| --- | --- | --- | --- |
| `02-a` | `contracts/runs.ts` | `cost_usd: z.number()` narrowed to `.nullable()` — consumers now format `null` | WARNING |
| `02-b` | `contracts/runs.ts` | `RunStatus` loses `'queued'`; the route relabels those runs `'running'`, so an existing value changes meaning too | CRITICAL |
| `02-c` | `routes/runs.ts` | an unknown repo now returns `200` with an empty page instead of `404` — a caller's "does this repo exist" check silently inverts | CRITICAL |

### `03-findings-surface` — reads like tightening up an endpoint

| id | File | Planted change | Severity we expect |
| --- | --- | --- | --- |
| `03-a` | `routes/findings.ts` | route path moved from `/findings` to `/review-findings`, no alias | CRITICAL |
| `03-b` | `contracts/findings.ts` | `agentId` added as a **required** query parameter — every existing request 422s | CRITICAL |
| `03-c` | `contracts/findings.ts` | severity `'suggestion'` renamed to `'nit'` — clients switching on it fall through | CRITICAL |

### `04-additive-only` — the control

Nothing is planted: an optional `draft` field, an appended `timed_out` enum
value, a brand-new `/reviewers` endpoint, and a correct minor bump to 2.4.0.
The expected result is **no findings**. A `SUGGESTION` noting that consumers
must tolerate unknown enum values is within the noise floor (both models did
this at least once, and both still returned `approve`); a `WARNING` or
`CRITICAL` here is a false positive and the reviewer is over-reporting.

A reviewer that finds four of nine is telling you about the reviewer, not about
the code. That is what the table is for.

## Running the A/B

The harness is `evals/` at the repo root; this directory is the material it
reads. See `evals/README.md` for the full options.

```sh
cd evals && npm install
npm run eval -- --suite api-contract-reviewer
npm run eval -- --suite api-contract-reviewer --cases 01,03 --model claude-haiku-4-5
```

Both arms use the same system prompt, the same diff, the same model and
`strategy: 'single-pass'`. The only difference is whether the four skill bodies
are in the `skills` prompt slot — exactly what linking or unlinking them in the
Skills tab changes. `expected.json`'s `agent` block is what says so: three of
the four skills resolve out of the DB seed (`seed:`) and the fourth out of this
folder's parent (`file:../deprecation-policy.md`). No database and no running
server is needed either way.

A run costs real money: about $0.10 per arm on `claude-opus-5` and $0.02 on
`claude-haiku-4-5`, so a full eight-arm sweep is roughly $0.80 and $0.15.

## What the first runs measured

Reports are in `evals/results/`.

| Model | without skills | with skills |
| --- | --- | --- |
| `claude-opus-5` | 9/9 | 9/9 |
| `claude-haiku-4-5` | 9/9 | 6/6 on the cases it completed; case 01's arm failed |

**The skills did not change what was detected.** On these diffs, at both model
tiers, the agent's system prompt alone found every planted change; the skills
changed how the finding was *argued* (they supply the vocabulary — deprecation
window, `@deprecated` marker, changelog under a Breaking heading) and cut the
Opus arm's output tokens roughly in half on case 01. On Haiku the `with-skills`
arm of case 01 failed structured-output validation three times in a row — the
longer prompt costs that model schema compliance.

Two things follow. The skill README's claim that an unskilled reviewer reads the
rename as tidy-up holds against the cheap default model
(`deepseek/deepseek-v4-flash`) it was written for, not against Claude. And these
cases are textbook: to discriminate at the Claude tier the planted changes need
to be subtler — a changed default, an error-body shape change, a behaviour
change to a path that is already `@deprecated`.

If you add a case, add its rows above and to `expected.json`, and re-run
`./make-diffs.sh`. The table is what makes this suite a measurement rather than
a pile of breaking changes.
